Build plan · office coffee run

Coffee
Run

One link on everyone's phone. Type your name once, tap your drink, and the person going downstairs gets a tidy docket for the counter.

Below: eight ways to build it (picked for what they teach and how they read on a CV), the one data idea that makes all of them simple, and two interactive designs you can poke at right now.

Your spec

  • Open a URL on your phone
  • Enter your name as rarely as possible
  • Add your order from an autocompleting list
  • Orders clear every day
  • Browse previous days
  • View 1: aaron – matcha, alex – matcha
  • View 2: matcha × 2

The one idea

One table, two queries, no deletes

Every option below shares this core. Orders are stamped with the office's date. "Clearing" each day is just filtering by today, so the history comes free. Both master views read the same rows, one listed by person and one grouped by drink.

Watch the time zone. If "today" is computed in UTC, an office in Sydney (UTC+11 in October) would see the list clear at 11am, right in the middle of the run. Compute :today in the office's zone, on the server.

Spec to solution

How each requirement gets met

Open a URL on your phoneA mobile-first web app with a short link, plus a QR code stuck on the kitchen fridge. Make it an installable PWA so it sits on the home screen like an app.
Enter your name rarelyOn first visit the server creates a person and sets a long-lived HttpOnly cookie holding a random ID. Don't rely on localStorage alone: Safari clears script-written storage after 7 days without a visit, which a two-week holiday will trigger. On a new phone you tap your name from the list. Passkeys are the upgrade if you want it to feel slick.
Autocomplete to a set listA menu table, fuzzy-matched as you type, ranked by what this office actually orders. Your own usual sits at the top as a one-tap "same as yesterday".
Clears every dayNothing gets deleted and nothing needs a midnight cron job. Today's views filter by today's date.
See previous daysThe same query with a different date, behind a ‹ › day switcher.
Two master viewsTwo read-only queries over the same rows (see above). Push changes live over WebSockets or Server-Sent Events so the clerk's screen updates while they walk to the café.

Eight ways to build it

Pick the stack for what you want to learn

The app is small enough that any of these will work. The difference is what you walk away knowing and how it sounds in an interview. Ratings are my judgement, out of five.

The stack most job ads ask for right now. React server components render the lists, server actions handle "add my order", Drizzle or Prisma talks to Postgres. Hosted Postgres like Neon or Supabase gives you a free database, and Supabase Realtime pushes new orders to every phone.

AWS serverless with CDK

Edge-native

Cloudflare Workers + Durable Objects

One Durable Object per office per day acts as a tiny stateful server. It holds today's orders in memory, writes them to its built-in SQLite storage, and keeps a WebSocket open to every phone. History goes to D1. Global, instant and almost free.

The architect's answer

Event sourcing + CQRS in .NET or Kotlin

Store what happened (OrderPlaced, OrderChanged, OrderCancelled) instead of current state. Your two master views become two projections built from the same event stream, which is exactly the CQRS pattern. History, undo and "what did the office drink in March" all fall out of the log.

If it's for the CV

Next.js + Postgres, built like a professional

The stack matters less than the habits around it. These are what make a small project read as real engineering:

  • Realtime updates on both master views
  • Playwright tests that place orders and check the tally
  • GitHub Actions running lint, types and tests on every push
  • Docker for local Postgres, migrations checked in
  • Accessible forms and a README with screenshots
  • Real users: your office, with a usage number to quote

If it's for the fun of it

Phoenix LiveView, or Durable Objects

Both make realtime feel effortless and will change how you think about where state lives. LiveView teaches you a new language and a new model of UI. Durable Objects teach you the edge and the actor model in a few hundred lines of TypeScript.

Either way, borrow the event-sourcing idea: log every order change. It costs one extra table and gives you a great "what I learned" story.

Two designs · interactive

Try it: both designs share one live order list

These are working mockups with example people. Change your name, type into the drink box to see the autocomplete, add an order, then watch it show up in both master views. Tap a line on the clerk's docket to tick it off. Nothing is saved; reload to reset.

Design A

The Docket

Styled like a café's own thermal-printed order ticket. Monospace type, dashed rules and dotted leaders between name and drink. The clerk's view is literally a docket you can hold up to the barista, and ticking a line strikes it through in red pen. Quiet, legible, and a bit of a wink at the subject.

Design B

Cup Board

A dark, thumb-first app. Big rounded targets, pill toggles for size and milk, a colored avatar for each person so you can find yourself at a glance. The clerk's view is a grid of oversized counts readable at arm's length on a busy counter, and tiles turn green as drinks get made.

Details that make it feel finished

The small things people notice

Name once, really

Server-set cookie with a random ID, refreshed on each visit. Browsers cap cookie lifetime at around 400 days, so refreshing keeps it alive indefinitely. New phone? Tap your name on the list. Want to go further? Passkeys via WebAuthn mean Face ID gets you back in on any device.

Autocomplete that learns

Fuzzy match on the menu (Fuse.js on the client, or Postgres pg_trgm on the server), then sort by how often this office orders each drink. "lat" should offer latte, flat white and matcha latte, with the popular one first.

The clerk's screen

Big type and a Screen Wake Lock so the phone doesn't dim at the counter. Tap to tick off each drink. A "copy as text" button for pasting into Teams or Slack, or reading out to the barista.

Normalise the order

Store drink, size, milk and extras as separate fields, not free text. That's what lets "Oat flat white" from two people collapse into "2 ×" on the docket instead of appearing as two near-duplicate strings.

One order per person

A unique key on (day, person). Adding again replaces your order rather than duplicating it, and the button says "Update my order" so nobody's surprised.

A cut-off

Whoever's going taps "Leaving now". It locks the list, pushes a notification to everyone who hasn't ordered, and stamps the docket with a time. This is a nice place to add Web Push.

Build order

A sensible path from zero to the office using it

  1. Static prototype

    Click through a mockup like the ones above with hard-coded data. Show it to two colleagues and fix what confuses them.

  2. Schema and the name cookie

    Set up the database, migrations, the person table and the first-visit flow. Prove a phone stays remembered after a restart.

  3. Add an order and both master views

    The menu table, autocomplete, the upsert, and the two queries. At this point it's usable, so ship it to the office.

  4. Realtime and history

    Live updates over WebSockets or SSE, the day switcher, and "same as yesterday".

  5. Tests, CI and a proper deploy

    Playwright end-to-end tests for the full order flow, a GitHub Actions pipeline, preview deployments, error tracking.

  6. Stretch goals

    Passkeys, installable PWA, push notification at cut-off, stats on the office's caffeine habit, multiple offices.
