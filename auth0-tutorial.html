Keeping an Auth0 token alive

Store an Auth0 token in the Go server and keep it valid for as long as Auth0 allows, by spending the refresh token at the right moment and never losing the new one.

00

What token do you have?

"An Auth0 token" can mean three different things. Only one of them can be kept alive, so check this first. Paste your token response somewhere private and look at which fields it has.

FieldWhat it isLifetime
access_tokenWhat you send to an API as Authorization: Bearer …. Usually a JWT (starts eyJ).Short. 24 hours by default for an API.
id_tokenWho logged in (name, email). For your app to read, never sent to APIs.Short.
refresh_tokenA long-lived secret you trade at Auth0 for a fresh access token. Not a JWT, just an opaque string.Long. Days to a year, or forever (see next section).

If you only have an access_token, there is nothing to refresh with. It dies when it expires and you'd have to fetch another by hand. Two common reasons:

  • You copied it from the API's "Test" tab in the Auth0 dashboard. That is a client credentials (machine-to-machine) token. Auth0 never issues refresh tokens for that flow because it doesn't need to: the server holds the client secret and can just ask for a new access token whenever it likes. If this is your case, step 03 changes to grant_type=client_credentials and steps 01–02 get simpler (no refresh token to keep). Everything else in this tutorial still applies.
  • You logged in without the offline_access scope. Auth0 only hands out a refresh token when you ask for it.
Getting a refresh token by hand (authorization code flow)

In the Auth0 dashboard:

  1. Applications → APIs → your API → Settings: turn on Allow Offline Access.
  2. Applications → your app → Settings: add http://localhost:8080/callback to Allowed Callback URLs. Under Advanced → Grant Types, make sure Refresh Token is ticked.

Then open this in a browser (fill in the three values), log in, and copy the code= part out of the address bar. The page itself will 404, which is fine.

Swap the code for tokens. You have about a minute before the code expires.

The response now includes a refresh_token. That string is what this tutorial keeps alive.

Read the output before you do anything else. If it contains a new refresh_token, rotation is on, and the one you just sent is now spent. Keep the new one. The next section explains why.

How refreshing works

Auth0 has two settings that decide how this behaves. Both are under Applications → your app → Settings → Refresh Token Rotation / Refresh Token Expiration.

Rotation

Off: you send the refresh token, you get a new access token, and the refresh token stays the same. You could store it in an env var and never touch it again.

On: every refresh returns a new refresh token and the old one stops working. Auth0 also watches for reuse: if anyone sends an already-used refresh token, Auth0 assumes it was stolen and revokes the whole family, including the newest one. You're logged out and have to fetch a fresh token by hand. (SPAs always have rotation on.)

Rotation is what makes this harder than "put it in an env var". The refresh token changes all the time, so it has to live somewhere you can write to (a database row). You also have to be careful never to:

  • Lose the new one. If you get the response and crash before saving, you're holding a dead token. → step 05
  • Spend the same one twice. Two requests refreshing at the same moment both send the same token, and the second one looks like reuse. → step 04
sequenceDiagram
  participant A as Request A
  participant B as Request B
  participant Auth0
  A->>Auth0: refresh with rt-1
  Auth0-->>A: at-2, rt-2 (rt-1 now spent)
  B->>Auth0: refresh with rt-1 (same moment, old copy)
  Note over Auth0: rt-1 reused! Revoke rt-1, rt-2, everything
  Auth0-->>B: 403 invalid_grant

Expiration

SettingMeaningCan you beat it?
Idle lifetimeDies if not used for this long. Default 30 days.Yes. Refresh regularly even when nothing needs a token. → step 06
Absolute lifetimeDies this long after the original login, however often you refresh. Rotation does not reset it. Up to 1 year, or off.No. When it runs out, a person has to log in again. Your code should notice and say so clearly.
So, "for as long as possible" means

Refresh before the access token expires, which beats the idle timer for free. Save every rotated token straight away. When Auth0 finally says invalid_grant, stop retrying and log that a new token is needed. If this is your own Auth0 tenant and it isn't an SPA, you can also raise or turn off the absolute lifetime in those settings.

01

The table

Create db/migrations/0004_auth0_token.sql. db.Migrate picks it up by its number, the same way your earlier migrations ran.

You need: an id locked to 1, access_token, refresh_token, expires_at (unix seconds, 0 meaning "refresh now"), refreshed_at, and a nullable dead_reason.

Hint

To allow only one row: id INTEGER PRIMARY KEY CHECK (id = 1). A second row would need id 1 again, which the primary key refuses, and any other id fails the CHECK.

Give access_token and expires_at defaults ('' and 0), so seeding only has to supply the refresh token.

Answer
Why not hash it?

In session.go you store only a hash of each session token, so a leaked database can't sign anyone in. That works because you only ever need to check a session token. Here you need to send the refresh token back to Auth0, so you need the real value. A hash can't be reversed. If you want protection at rest, encrypt it instead (see Afterwards).

02

The store

Fill in Seed, Load, Save and MarkDead in store.go. They're all plain database/sql, like your sync handlers.

The one to think about is Seed. You'll put the first refresh token in an env var, and the server copies it into the table at startup. After the first rotation that env var holds a spent token. If a restart wrote it into the table again, the next refresh would send a spent token, Auth0 would see reuse, and everything would be revoked. So Seed must only ever insert when the table is empty.

Hint

INSERT OR IGNORE skips the insert when it would break a constraint, here the primary key on id 1.

For Load, scan dead_reason into a sql.NullString. Check for no row with errors.Is(err, sql.ErrNoRows). To let callers test for ErrDead and still see the reason, wrap it: fmt.Errorf("%w: %s", ErrDead, dead.String).

Answer
Rails

Seed is AuthToken.find_or_create_by!(id: 1) { |t| t.refresh_token = ENV[…] }, but done in a single statement, so there's no gap between the find and the create.

03

Call Auth0

Write Config.refresh in client.go. It's the curl from step 00, written in Go. You've written handlers that receive HTTP. This is the other side, sending it.

Sorting the errors correctly matters more than the request itself, because the caller does different things with each kind:

Hint

url.Values{"grant_type": {"refresh_token"}, …} builds the form, and .Encode() turns it into a=b&c=d. Wrap that in strings.NewReader for the body.

Always defer res.Body.Close() once hc.Do succeeds. Otherwise the connection is never reused, and a long-running server slowly leaks them.

json.NewDecoder(res.Body).Decode(&body) fills the struct. Success and failure responses share the same struct because the JSON field names don't overlap.

Answer
Rails

It's Faraday.post(url, form), but Go's client doesn't raise on a 4xx or 5xx. err is only set when no response came back at all, so you have to check res.StatusCode yourself.

04

One refresh at a time

Write Source.AccessToken. Anything that needs a token calls it: load the row, return the access token if it has more than 5 minutes left, otherwise refresh.

Remember the reuse diagram. net/http runs every request in its own goroutine, so twenty requests can arrive in the same millisecond, all see an expired token, and all refresh with the same refresh token. That's nineteen reuses and a revoked family. TestConcurrentCallersRefreshOnce does exactly this.

The fix is a sync.Mutex around the whole check-then-refresh. The first caller refreshes. The other nineteen wait at Lock(), then load the row again, find it fresh, and return without calling Auth0.

Hint

s.mu.Lock() then defer s.mu.Unlock() as the first two lines. defer means "run this when the function returns, however it returns", like ensure.

Load the row inside the lock. If you loaded it before locking, waiters would decide based on an old copy.

Answer
Rails

Puma with several workers is several processes, so a Ruby Mutex wouldn't be enough. You'd need with_lock (a row lock in the database) or a Redis lock. Coffee Run is one Go process, so an in-memory mutex covers every request. If you ever ran two copies of the server, you'd be back to needing the database lock.

Try it

Once it passes, comment out the two lock lines and run go test -race -run Concurrent ./internal/auth0/. Watch it fail, then put them back.

05

Save, whatever happens

Write refreshLocked: call Auth0, build the new Token, save it, return it. The interesting part is the first line.

Every Go request handler has a context.Context that gets cancelled when the client goes away (phone closes the app, request times out). Code that respects ctx stops at that moment. Usually that's what you want. Here it's a trap:

  1. The refresh request reaches Auth0. Auth0 spends rt-1 and sends back rt-2.
  2. The phone that triggered it closes the tab, so ctx is cancelled.
  3. Your code abandons the response, and rt-2 is never saved.
  4. The table still holds rt-1, which is spent. Next refresh is reuse, and everything is revoked.

context.WithoutCancel(ctx) gives you a context that keeps the parent's values but ignores its cancellation. Once you've started spending a refresh token, you finish the job. The HTTP client's 30 second timeout still stops it from hanging forever.

Hint

cmp.Or(a, b) returns the first value that isn't empty. With rotation off, Auth0 sends no refresh_token, so cmp.Or(res.RefreshToken, old.RefreshToken) keeps the one you have.

expires_in is seconds as an int. Convert it with time.Duration(res.ExpiresIn) * time.Second.

On errRejected, call MarkDead before returning, so the next caller gets ErrDead from Load without bothering Auth0 again.

Answer
Order matters

Save first, then return. Don't start using the new access token until the new refresh token is on disk. If the process dies between those steps, you want to lose a cheap thing (an access token you can get again), never the refresh token.

06

Refresh ahead of time

Steps 04–05 refresh only when something asks for a token. If nobody asks for 30 days, the idle timer kills the refresh token. Run is a background loop that sleeps until 5 minutes before expiry, then refreshes. That uses the refresh token about once a day, every day.

It has to handle three outcomes differently:

  • Success: loop again. The next wait comes from the new expires_at.
  • ErrDead (or no token): log it and return. Retrying a rejected token can't succeed.
  • Anything else: wait and retry, doubling the wait each time (1 min, 2, 4 … capped at 30). Without a wait, a failure would retry thousands of times a second. (My first draft of the answer had exactly that bug.)
Hint

The sleep helper is written for you. It returns false if ctx was cancelled during the wait (server shutting down), and then you just return.

Wait time = tok.ExpiresAt.Add(-leeway).Sub(s.now()). A freshly seeded row has expires_at = 0 (1970), so the wait is negative. Use max(wait, 0), which makes the first refresh happen at startup.

Write a switch { case err == nil: … case errors.Is(err, ErrDead): … default: … }. A switch with no value is Go's tidy if/else-if chain.

Answer
Rails

In Rails this would be a recurring job (sidekiq-cron, solid_queue's recurring tasks) plus a worker process. In Go it's go tokens.Run(ctx) in main: a goroutine that lives as long as the server. No queue, no extra process.

07

Bearer on every request

Now make the token easy to use. Source.Client() returns an *http.Client whose Transport adds Authorization: Bearer … to every request. Code that calls the protected API never sees a token. It just uses this client.

A Transport is anything with a RoundTrip(*http.Request) (*http.Response, error) method. You only fill in bearer.RoundTrip.

Hint

The rule for RoundTrippers is that they must not change the request they're given, because the caller may still be using it. So r = r.Clone(r.Context()), set the header on the clone, then return http.DefaultTransport.RoundTrip(r).

Answer
Rails

This is Faraday middleware, conn.request :authorization, 'Bearer', -> { token }. Go's version is an interface with one method, and interfaces are satisfied implicitly. bearer never says "implements RoundTripper". Having the method is enough.

Wire it into main.go

All eight tests should be green now. Last step: start it in cmd/server/main.go, after db.Migrate. Only start it if AUTH0_DOMAIN is set, so go run without Auth0 config still works.

Answer

Try it locally with your real values:

AUTH0_DOMAIN is the bare host

The code always builds "https://" + AUTH0_DOMAIN + "/oauth/token", so set it to dev-xxxx.us.auth0.com, not https://dev-xxxx.us.auth0.com/, or you'll get https://https://…. The tests run the fake Auth0 over real TLS, and it refuses anything that isn't an HTTPS POST to /oauth/token.

On clanker

Put the four AUTH0_* values wherever /opt/coffee-run/deploy.sh gets its environment for docker run (an --env-file is the tidy way). Keep them out of the Dockerfile and out of git. The table lives in the same SQLite file as everything else, so as long as that's on a volume, the rotated token survives redeploys.

When it dies

When the absolute lifetime runs out you'll see auth0: stopping refresh loop: … rejected in the logs. To recover, get a new refresh token (step 00), then DELETE FROM auth0_token; so Seed will accept it, update the env var, and restart.

Afterwards

The library version

golang.org/x/oauth2 covers steps 03, 04 and 07: conf.TokenSource(ctx, tok) refreshes when needed, oauth2.ReuseTokenSource caches the token behind a mutex, and oauth2.NewClient is your bearer client. It does not save a rotated refresh token for you or run ahead of time. You'd still write steps 01, 02, 05 and 06 as a wrapping TokenSource. Now that you've built it by hand, you'll recognise each piece if you switch.

Stretch goals

  • Encrypt at rest. AES-GCM (crypto/aes + crypto/cipher) with a 32-byte key from an env var, used in Save and Load. Then a copied coffee-run.db no longer contains a working credential.
  • Status endpoint. GET /api/auth0 returning refreshed_at, expires_at and dead_reason, never the tokens themselves, so you can see it's healthy without SSH.
  • Reuse interval. In Auth0's rotation settings you can allow the previous token to be reused for a few seconds. That's a safety net for step 05's crash case: a retry with the old token gets a new one instead of revoking everything.
