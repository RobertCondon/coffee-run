Coffee Run in Go

Is Go worth learning?

Yes. Go is a mainstream professional language, especially for backend services, infrastructure and developer tools.

  • The tools you already use are written in it. Docker, Kubernetes, Terraform, Prometheus, Caddy and Hugo are all Go. So are big parts of Google, Uber, Cloudflare, Twitch and Dropbox.
  • People use it for work, not just side projects. In the Go team's 2025 developer survey, 82% of respondents said they use Go at work (summary). That's a survey of Go users, so it shows how Go is used, not how popular it is overall.
  • Go jobs exist in New Zealand, but the market is smaller. JobsPipe counts 39 companies hiring in NZ whose job ads point to Go: 7 confirmed and 32 likely, including Xe.com, Level and Propellerhead. My read is that most NZ backend ads ask for C#/.NET, Java, TypeScript or Python, and Go shows up more in platform, infrastructure and fintech teams. Often it's listed as a second language. To check this yourself, search Seek for "golang".

For your CV, Go reads well beside TypeScript: it shows you can work outside the JavaScript world. And this project uses the things Go is known for: a fast HTTP server, concurrency for live updates, and a single binary you can copy to a server.

What you're building

Every phone keeps a small SQLite database. The app reads and writes that local copy, so it's instant and works offline. A sync loop moves changes between the phone and the server. The server is one Go program that also serves the phone app.

The one habit to build

Handle every error where it happens: if err != nil { return err }. It looks noisy for a day, then you start to like always knowing where a failure goes. To add context, wrap it: fmt.Errorf("migration %s: %w", name, err).

04

Open SQLite and run migrations

Use modernc.org/sqlite. It's SQLite translated into pure Go, so you don't need a C compiler, and building for Linux from your Mac just works.

Instead of a migration library, write a 40-line runner. SQLite has a spare integer in every database file, PRAGMA user_version. Store the number of the last migration that ran there. //go:embed puts the SQL files inside the binary.

Go concepts

The blank import _ "modernc.org/sqlite" runs the package's setup code, which registers the driver with database/sql. database/sql is Go's equivalent of the database half of ActiveRecord: a connection pool plus Query, Exec and transactions. defer tx.Rollback() is the standard pattern. If the function returns early, the transaction rolls back. After Commit, the rollback does nothing.

Why these pragmas

WAL lets reads continue while a write happens. busy_timeout waits instead of failing when the database is locked. _txlock=immediate takes the write lock at BEGIN, which avoids a classic SQLite deadlock. One open connection is plenty for an office and keeps everything simple.

Schema and the two views

Every table the phone syncs has a version column. sync_state holds one counter. Each server write takes the next number and stamps it on the rows it touched. Deletes set deleted_at instead of removing the row (a tombstone), so phones find out about them.

Now the views. These are your two master screens: “who ordered what” and the clerk's docket. Write them once. The phone runs this same file.

SQLite vs Postgres

SQLite has no stored functions, so the drink label is built in a plain CASE expression. It has no time zones, so “today” is worked out in Go and passed in. Extras are stored as sorted JSON text and read back with json_each, which works the same in the browser's SQLite.

Try it

Why this is safe

SQLite allows one writer at a time, so versions are committed in order. A phone that has seen version 41 can never miss a row stamped 40. On Postgres you'd need extra care for this; here it comes free.

Identity. Someone types their name once. The server creates a person and a random session token, stores only a hash of the token, and puts the token in a long-lived HttpOnly cookie. After that, the phone remembers them. crypto/rand.Text() gives a random 26-character string.

07

Pull: “what changed since N?”

The phone keeps a cursor, the highest version it has seen. GET /api/sync?since=41 returns every row with a higher version, plus the new cursor. All three reads share one transaction, so they see the same snapshot.

A small generic helper keeps the three queries short. Go has had generics since 1.18; you'll mostly use them for helpers like this.

In Rails terms

The pull is Order.where("version > ?", since) rendered as JSON. In Go you scan columns into struct fields by hand. That's more typing, but nothing is hidden. Once you're comfortable, look at sqlc: it writes this code for you from SQL.

08

Push: the outbox

The phone sends its queued writes as a list of ops. Each op gets its own result. If one is rejected, for example because the order is for a day that has closed, the response is still a 200 with a reason. The phone drops that op instead of retrying it forever.

The order ID is day:person_id, so each person has one order per day. The phone can work out the ID offline, and sending the same op twice changes nothing. The server never trusts the person ID from the phone. It uses the session's.

Validation lives in its own file. Sorting the extras means “vanilla + shot” and “shot + vanilla” land on the same docket line.

09

Live pings with goroutines

When anything is written, each open phone should hear about it in under a second. Use Server-Sent Events: one long HTTP response the server writes lines into. They're simpler than WebSockets and the browser reconnects by itself. The ping carries no data. It just means “pull now”.

The hub is a set of channels behind a mutex:

Each phone's /api/events request runs in its own goroutine. Go's server does that for you. The handler waits on three things with select: the phone leaving, a ping, or a 25-second keep-alive tick.

This is the bit Go is good at

Each connected phone costs one goroutine, a few kilobytes. select waits on several channels at once, and r.Context().Done() closes when the phone disconnects, so cleanup is a defer. In Rails, you'd use Action Cable for this.

Try it

In one terminal run curl -N -b jar localhost:8080/api/events. In another, run the upload from step 8. You'll see event: changed arrive immediately.

The phone app

The phone app is a React app made with Vite. Its database is sqlite-wasm (SQLite's official browser build) stored in OPFS, the browser's private file system. Ship it to clanker

Build the web app into web/dist, and the Go build embeds it. You get one file that holds the API, the app and the migrations.

Run it as a service, with the database somewhere permanent:

Point coffee.piwakawaka-flutter.com at it the same way as your other subdomains. The PWA needs HTTPS. If you use Caddy, it's two lines, and Caddy handles SSE correctly:

If you use nginx instead, turn off buffering on /api/events (proxy_buffering off;) or the pings will arrive late. The proxy should also send X-Forwarded-Proto, which is how the server knows to set the cookie as Secure.

Backups: run Litestream beside it. It streams every change in the SQLite file to S3-compatible storage, such as Backblaze B2 or Cloudflare R2, and can restore it to any point in time.

Try it

Open the URL on your phone, sign in, add to home screen, order. Then sudo systemctl restart coffee-run and watch the app reconnect by itself.

What next

  • History screen: phones keep 14 days. Add GET /api/history?day=… for older days, read straight from v_order_line on the server.
  • “Leaving now”: a run table, so whoever goes down can close the day's orders.
  • Menu editing: a small admin page, or just sqlite3 for now. Bump the version so phones notice.
  • Graceful shutdown: signal.NotifyContext plus srv.Shutdown, so restarts don't cut requests off.
  • Structured logs: swap log for log/slog.
